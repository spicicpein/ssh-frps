# winssh-tunnel

Один Go-бинарник для Windows = встроенный SSH-сервер (с настоящим
интерактивным шеллом через ConPTY) + встроенный клиент frp, который
пробрасывает этот SSH (и любые другие TCP-сервисы: RDP, SMB и т.д.)
наружу через твой frps-сервер. Отдельный `frpc.exe` не нужен вообще —
всё в одном exe, без внешних DLL.

Сценарий: у тебя есть Windows-машина за NAT (дома, в офисе), без
белого IP, и VPS с frps. winssh-tunnel сам дозванивается с Windows на
VPS и открывает туда постоянный обратный туннель — подключаешься к
Windows-машине через VPS, как будто она сама торчит наружу.


## Быстрый старт

1. Скачай `winssh-tunnel.exe` и `frpc-example.toml` в одну папку на
   Windows-машине.
2. Скопируй `frpc-example.toml` → `frpc.toml`, открой в блокноте,
   заполни: адрес VPS, токен (совпадает с `auth.token` в `frps.toml`
   на VPS) и пароль для входа. Подробности каждого поля — прямо в
   комментариях самого файла.
3. Убедись, что на frps включён SSH Tunnel Gateway (см. раздел
   "Перед первым запуском" ниже).
4. Дважды кликни `winssh-tunnel.exe` — ключ для связи с frps и
   `host_key` (сертификат встроенного sshd) программа создаст сама
   при первом запуске. Если Windows спросит про брандмауэр — разреши.
5. Проверяй с другого компьютера:
   ```
   ssh -p 65000 user@ВАШ_VPS_IP
   ```
   (порт — тот, что указал как `remotePort` у прокси `winssh` в
   конфиге; пароль — тот, что ввёл в `winsshPassword`; имя
   пользователя может быть любым, программа проверяет только пароль).

Хочешь, чтобы это работало постоянно и переживало перезагрузку
Windows — переходи в раздел "Установка как служба" ниже.


## Перед первым запуском

**На frps должен быть включён SSH Tunnel Gateway.** Добавь в
`frps.toml` на VPS, если ещё нет:
```toml
sshTunnelGateway.bindPort = 2200
```
Это отдельный порт, существующие обычные frpc/frps-туннели не
трогает. Если у frps не задан `sshTunnelGateway.authorizedKeysFile` —
ключ клиента не проверяется вообще, доступ регулируется только
обычным `auth.token`. Сверь по актуальному конфигу своего frps.

Дальше всё остальное winssh-tunnel делает сам: генерирует ключ для
исходящего соединения (`%USERPROFILE%\.ssh\id_rsa`, если его ещё
нет) и `host_key` (сертификат встроенного sshd) — без единого
ручного шага вроде `ssh-keygen`.


## Установка как служба Windows

Из командной строки **от имени Администратора**:

```cmd
winssh-tunnel.exe -i
winssh-tunnel.exe --install
```
Ставит службу с настройками по умолчанию:
- ключ в реестре (Service name): `frpwin`
- отображаемое имя (services.msc): `Frpwin`
- описание: `Windows frp`
- конфиг: `frpc.toml` рядом с exe
- автозапуск при загрузке Windows, авто-restart при падении

Дальше:
```cmd
winssh-tunnel.exe start     # запустить прямо сейчас
winssh-tunnel.exe stop      # остановить
winssh-tunnel.exe --uninstall
```

### Кастомный путь/имя конфига

```cmd
winssh-tunnel.exe -i -c C:\путь\до\frpc.toml
winssh-tunnel.exe -i -c C:\путь\до\another.name
```
Программа переходит в папку УКАЗАННОГО конфига (не обязательно в
папку exe) — там же ищет/создаёт `host_key`.

### Кастомные имя/описание службы, несколько инстансов на одном exe

```cmd
winssh-tunnel.exe -i -c C:\configs\office\frpc.toml -k office-ssh -n "Office SSH" -d "Туннель до офисного ПК"
winssh-tunnel.exe -i -c C:\configs\home\frpc.toml   -k home-ssh   -n "Home SSH"   -d "Туннель до домашнего ПК"
```
`-k` — ключ в реестре (должен быть уникальным для каждого инстанса).
`start`/`stop`/`--uninstall` тоже принимают `-k`, чтобы управлять
конкретным инстансом:
```cmd
winssh-tunnel.exe start -k office-ssh
winssh-tunnel.exe --uninstall -k home-ssh
```
Без `-k` везде подразумевается `frpwin` (дефолт).

| Флаг | Длинная форма | Назначение | По умолчанию |
|---|---|---|---|
| `-i` | `--install` | установить службу | — |
| `-u` | `--uninstall` | удалить службу | — |
| — | `start` | запустить установленную службу | — |
| — | `stop` | остановить службу | — |
| `-c` | `--config` | путь к файлу конфига | `frpc.toml` рядом с exe |
| `-k` | `--key` | ключ в реестре / имя службы | `frpwin` |
| `-n` | `--name` | отображаемое имя (services.msc) | `Frpwin` |
| `-d` | `--desc` | описание службы | `Windows frp` |

Логи службы — в Event Viewer (Просмотр событий → Журналы Windows →
Application) и, конечно, в `services.msc` — там служба видна со
своим отображаемым именем.

**Честно про graceful shutdown:** при остановке служба завершается
жёстко (нет промежуточного состояния, которое было бы жалко
потерять — `host_key`/ключ уже на диске). Активные SSH-сессии при
этом просто рвутся, как при обрыве связи.


## Стартовая папка после входа

Поле `shellDir` в `frpc.toml` — куда попадаешь сразу после входа по
SSH (и откуда выполняются одиночные команды вида
`ssh user@vps -p 65000 dir`). Поддерживает переменные окружения
Windows (`%USERPROFILE%`, `%SystemDrive%` и т.д., включая склейку без
разделителя). Подробности и примеры — в комментариях
`frpc-example.toml`.


## Как это работает

Два *независимых* SSH-разговора — оба используют протокол SSH, но
это не одно и то же, и у них разная аутентификация:

1. **Наружу, Windows → frps** (встроенный клиент frp, `tiny-frpc`) —
   по ключу. Это ограничение самого tiny-frpc: он всегда берёт ключ
   из `%USERPROFILE%\.ssh\id_rsa`. Но ты его никогда не вводишь и не
   видишь — генерируется один раз при первом запуске, дальше
   программа читает файл сама.
2. **Внутрь, клиент → Windows** (встроенный sshd) — по паролю.
   Пароль сравнивается constant-time (защита от timing-атак), плюс
   троттлинг: после каждой неудачной попытки с одного IP — растущая
   задержка (до 30 сек), так что тупой перебор станет мучительно
   медленным без дополнительной возни с твоей стороны.

Встроенный sshd слушает на **двух** локальных адресах отдельными
listener'ами — `127.0.0.1:PORT` (IPv4) и `[::1]:PORT` (IPv6), а не
одним "универсальным" `:PORT`. Это не просто перестраховка: на
Windows один dual-stack сокет иногда не отдаёт IPv4-соединения в
Accept() корректно (TCP-хендшейк на уровне ОС проходит, но данные до
приложения не доходят) — именно так тихо ломался туннель, пока это
не всплыло и не было исправлено. tiny-frpc дозванивается на
127.0.0.1, так что явный IPv4-listener — не опция, а необходимость.


## Проброс портов кроме SSH (RDP, SMB и т.д.)

Работает без пересборки exe — просто добавь ещё `[[proxies]]` в
`frpc.toml` (примеры для RDP и SMB закомментированы в
`frpc-example.toml`) и перезапусти программу. Список прокси читается
из конфига целиком, не завязан на SSH — проверено на трёх прокси
одновременно (ssh+rdp+smb), все регистрируются независимо.

Границы, о которых стоит знать:
- Поддерживаются типы `tcp`, `http`, `https`, `tcpmux`, `stcp` — тот
  же набор, что умеет разбирать tiny-frpc. **UDP не поддерживается
  вообще** — но RDP и SMB на UDP не завязаны, так что для типичных
  сценариев это не проблема.
- Это по-прежнему идёт через tiny-frpc и SSH Tunnel Gateway, а не
  через нативный протокол официального `frpc` — см. оговорку про
  "preview version" в разделе "Ограничения" ниже. Если RDP/SMB для
  тебя — критичная постоянная инфраструктура, может быть разумнее
  гонять их через официальный `frpc.exe` отдельным процессом, а
  winssh-tunnel оставить только под SSH как аварийный вход. Оба
  варианта спокойно уживаются на одном frps одновременно.


## Кодировка (кириллица в консоли)

`cmd.exe` по умолчанию пишет в OEM-кодировке консоли (обычно CP866
на русской Windows), а SSH-клиенты (PuTTY/KiTTY и т.д.) чаще всего
ждут UTF-8 — без вмешательства получились бы кракозябры. Программа
сама переключает кодовую страницу на UTF-8 (`chcp 65001`) сразу
после старта сессии — и для интерактивного шелла, и для одиночных
команд. Первые две строки баннера (`Microsoft Windows [Version...]`
и copyright) `cmd.exe` успевает напечатать ДО того, как прочитает эту
команду — они могут разово остаться в старой кодировке при каждом
подключении, это чисто косметика. Всё остальное — уже корректный
UTF-8.

Убедись, что у твоего SSH-клиента (PuTTY/KiTTY: Window → Translation
→ Remote character set) стоит **UTF-8** — обычно так по умолчанию в
современных версиях.


## Минимальная версия Windows

**Windows 10, сборка 1809 (October 2018 Update) / Windows Server
2019 — и новее.** Это жёсткий минимум для интерактивного шелла: он
использует ConPTY — системный API, которого попросту не существует
на более старых версиях Windows. Без ConPTY интерактивный вход
откажется работать с понятной ошибкой в логе — но **не-интерактивные
команды** (`ssh host команда`) и **SFTP** от ConPTY не зависят и
должны работать даже на старых системах, так как используют только
обычные pipe'ы, без псевдотерминала.

Для реально старых систем (Windows 7 / 8 / 8.1, Server 2008R2 / 2012
/ 2012R2) в проекте есть исходники legacy-варианта интерактивного
шелла — через `winpty` (предшественник ConPTY, обходит проблему
скрытым консольным окном вместо системного API) вместо ConPTY, см.
`shell_windows_legacy.go` и `BUILD-LEGACY.md`. **Честно:** это
отдельная сборка (`-tags legacy`, Go 1.20, требует `winpty.dll` и
`winpty-agent.exe` рядом с exe) — сегодня она не пересобиралась и не
тестировалась заново вместе со всеми последними изменениями (dual
listeners, служба, `shellDir`, chcp-фикс). Код для неё поддерживается
в актуальном состоянии (те же фиксы применены и туда), но
опубликованного бинарника для старых систем пока нет — если он тебе
нужен, скажи, соберём и проверим отдельно.


## Ограничения (честно, по текущему состоянию)

- **tiny-frpc сам себя называет preview-версией** — в его README
  прямым текстом написано "not for production, compatibility not
  guaranteed". Протокол SSH Tunnel Gateway стабилен с frps v0.53.0.
- **UDP не поддерживается** (ограничение tiny-frpc).
- Аутентификация входящих SSH-подключений — по паролю, не по ключу.
  Для личного использования это нормальный компромисс (плюс
  троттлинг на брутфорс); если понадобится вернуться на ключи —
  это откат одной функции (`PasswordAuth` → `PublicKeyAuth`), в
  истории проекта уже есть рабочая версия на ключах.
- Подключение к frps пока только напрямую — **SOCKS5/HTTP-прокси
  ещё не реализован** (если Windows-машина сидит за прокси без
  прямого выхода в интернет). Это следующий шаг в разработке.
- У службы нет graceful shutdown — остановка жёсткая (см. раздел
  "Установка как служба" выше).
- Один запущенный процесс = один встроенный sshd на один порт. Для
  нескольких независимых SSH-точек — используй несколько
  установленных служб с разными `-k`/`-c` (см. выше), каждая со
  своим конфигом и портом.
- `host_key`, `frpc.toml` (там и пароль, и токен) — держи рядом с
  конфигом, добавлены в `.gitignore`, не выкладывай публично.


## Файлы проекта

```
winssh-tunnel.exe            — готовый бинарник
frpc-example.toml            — пример конфига с подробными комментариями
main.go                      — конфиг, пароль, порт, ключи, sshd, tiny-frpc, разбор аргументов
service_windows.go           — установка/управление службой Windows (install/uninstall/start/stop)
service_other.go             — заглушка для не-Windows платформ
shell_windows_modern.go      — интерактивный шелл через ConPTY (Windows 10 1809+)
shell_windows_legacy.go      — интерактивный шелл через winpty (Windows 7+, отдельная сборка)
shell_other.go                — заглушка для linux/mac (нужна только для разработки/тестов)
sftp.go                        — SFTP-подсистема, общая для всех платформ
BUILD-LEGACY.md                — как собрать legacy-версию (Windows 7/Server 2008R2+)
```


## Сборка из исходников

```bash
go mod tidy
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -o winssh-tunnel.exe .
```
Go ≥ 1.22. Про сборку legacy-версии (другой Go, другие версии
зависимостей) — см. `BUILD-LEGACY.md`.
