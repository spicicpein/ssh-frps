# winssh-tunnel

## Быстрый старт (если не хочешь читать остальное)

1. Открой `frpc.toml` в блокноте, впиши адрес своего VPS вместо
   `ВАШ_VPS_IP_ИЛИ_ДОМЕН`. Сохрани.
2. Дважды кликни `setup.bat` — он спросит пароль для входа и впишет
   его в `frpc.toml`.
3. Дважды кликни `winssh-tunnel.exe`. Ключ для связи с frps она
   создаст сама при первом запуске. Если Windows спросит про
   брандмауэр — разреши.
4. Проверяй с другого компьютера: `ssh -p 6000 user@ВАШ_VPS_IP`
   (пароль — тот, что ввёл в шаге 2).

Дальше — подробности и что делать, если что-то не так.

Один Go-бинарник = встроенный SSH-сервер (gliderlabs/ssh, аутентификация
по паролю) + встроенный tiny-frpc-клиент, который дозванивается до
твоего frps через SSH Tunnel Gateway. frpc.exe не нужен вообще.

## Проброс портов кроме SSH (RDP, SMB и т.д.)

Работает, и без пересборки exe — просто добавь ещё `[[proxies]]` в
`frpc.toml` (примеры для RDP и SMB уже в файле закомментированы) и
перезапусти программу. Код читает список прокси из конфига целиком,
он не завязан на SSH — я проверил на трёх прокси одновременно
(ssh+rdp+smb), все три регистрируются независимо.

Границы, о которых стоит знать:

- Поддерживаются типы `tcp`, `http`, `https`, `tcpmux`, `stcp` — того
  же набора, что умеет разбирать tiny-frpc. **UDP не поддерживается
  вообще** — но RDP и SMB на UDP не завязаны (RDP при отсутствии UDP
  просто работает через TCP, это штатное поведение), так что для
  твоего случая это не проблема.
- Это по-прежнему идёт через tiny-frpc и SSH Tunnel Gateway, а не
  через нативный протокол официального frpc — то есть все оговорки
  про "preview version" из раздела ниже теперь касаются не только
  ssh-доступа, а вообще всех сервисов, которые через это пробрасываешь.
  Если RDP/SMB для тебя — это критичная постоянная инфраструктура, а
  не просто "иногда заглянуть", может быть разумнее гонять их через
  официальный frpc.exe (полнофункциональный, давно обкатанный) отдельным
  процессом, а наш бинарник оставить только под ssh как аварийный вход.
  Оба варианта одновременно спокойно уживаются на одном frps — можно
  начать с одного бинарника и добавить frpc.exe позже, если понадобится.

## Как это работает

Два *независимых* SSH-разговора — оба используют протокол ssh, но
это не одно и то же, и у них разная аутентификация:

1. **Наружу, Windows → frps** (tiny-frpc часть) — по ключу. Это
   ограничение самого tiny-frpc v0.1.3: он всегда берёт ключ из
   `%USERPROFILE%\.ssh\id_rsa`, без вариантов пароля — захардкожено
   в его коде, не в нашем. НО: ты его никогда не вводишь и не видишь —
   генерируется один раз при установке (без passphrase, `-N ""`),
   дальше бинарник читает файл сам, без единого твоего участия. Это
   не та боль, что с обычными ключами — тут просто файл, а не ритуал.
2. **Внутрь, клиент → Windows** (встроенный sshd, порт 2222) — по
   паролю. Это как раз то, что можно было поменять, потому что sshd —
   наш код. Пароль сравнивается constant-time (защита от timing-атак),
   плюс троттлинг: после каждой неудачной попытки с одного IP —
   растущая задержка (до 30 сек), так что тупой перебор станет
   мучительно медленным без дополнительной возни с твоей стороны.

Файлы кода, если будешь смотреть/менять:
- `main.go` — конфиг, пароль, порт, ключи, сборка ssh.Server, tiny-frpc
- `shell_windows.go` — настоящий интерактивный шелл через ConPTY,
  собирается только в Windows-версию (`//go:build windows`)
- `shell_other.go` — заглушка для linux/mac, нужна только чтобы я мог
  тестировать в песочнице; в твой .exe не попадает
- `sftp.go` — SFTP-подсистема, общая для всех платформ

## Перед первым запуском

1. **На frps (0.55.1) должен быть включён SSH Tunnel Gateway** —
   добавь в frps.toml, если ещё нет:
   ```toml
   sshTunnelGateway.bindPort = 2200
   ```
   Отдельный порт, существующие frpc/frps-туннели не трогает. Если у
   frps не задан `sshTunnelGateway.authorizedKeysFile` — ключ клиента
   не проверяется вообще, доступ регулируется только твоим обычным
   `auth.token`. Сверь по актуальному конфигу своего frps.

2. **Ключ для исходящего соединения программа создаёт сама** — при
   первом запуске проверяет `%USERPROFILE%\.ssh\id_rsa`, и если его
   нет, генерирует сама (раньше это был отдельный ручной шаг через
   ssh-keygen — теперь не нужно, ни тебе, ни setup.bat).

3. **Задай пароль для входа** — впиши его прямо в `frpc.toml`, поле
   `winsshPassword` (setup.bat делает это за тебя, спросив пароль
   один раз). Это наше собственное поле, не из схемы frp — frps его
   не видит, оно вообще никуда с Windows-машины не уходит, просто
   лежит в том же файле, что и остальные настройки. Если по каким-то
   причинам хочешь хранить пароль отдельно от конфига — работают и
   старые способы: переменная окружения `WINSSH_PASSWORD` (высший
   приоритет) или файл `password.txt` рядом с .exe.

4. **Заполни остальное в `frpc.toml`** — свой IP/домен VPS и токен.

## Сборка

```
go mod tidy
go build -o winssh-tunnel .
GOOS=windows GOARCH=amd64 go build -o winssh-tunnel.exe .
```

Нужен Go ≥ 1.24 (требование самого tiny-frpc). Нет под рукой — тот же
GitHub Actions раннер, что и для APK-пайплайна, подойдёт.

## Два бинарника: обычный и legacy (Windows 7 / Server 2008R2+)

ConPTY (на нём шелл в основной версии) и сам Go 1.24 требуют Windows 10
1809+ / Server 2019+ — на более старых системах не работают, тут без
вариантов. Для старых систем — **отдельный бинарник**, собран тем же
способом (Go из исходников), но с настоящим терминалом через winpty
(предшественник ConPTY, обходит проблему другим механизмом — скрытым
консольным окном, а не системным API) вместо урезанных голых пайпов:

- **`winssh-tunnel.exe`** — основной. Go 1.24, ConPTY, полноценный
  терминал. Windows 10 (1809+) / Server 2019+.
- **`winssh-tunnel-legacy.exe`** — под старое железо. Собран Go 1.20
  (последняя версия Go, поддерживающая Windows 7 / Server 2008R2 —
  подтверждено официальной вики golang) плюс winpty вместо ConPTY.
  Полноценный терминал (цвета, курсор, интерактивные программы) — не
  урезанная версия, в отличие от того, что было бы с голыми пайпами.
  Тянет Windows 7 / Server 2008R2 и новее.

**Важно про winpty: рядом с `winssh-tunnel-legacy.exe` обязательно
должны лежать `winpty.dll` и `winpty-agent.exe`** (тоже в комплекте).
Сознательно не стал вшивать их в exe через go:embed — самораспаковывающийся
exe чаще цепляет антивирусы, чем набор из трёх обычных файлов лежащих
рядом. Эти два файла — не мой код, а официальная сборка проекта
rprichard/winpty (релиз 0.4.3, msvc2015, x64), скачана напрямую с их
GitHub-релизов. Хэши для сверки:
```
winpty.dll:        936f611c2129600d35ab7aad45546a837f4f3a9ca7f673e5d66b48c313b9cd75
winpty-agent.exe:  9add1a61155ec47cf6f347faf776b746eebbde1dc9360d81b8a909da34650642
```

Код для обоих .exe один и тот же (main.go, sftp.go — общие),
различается только файл с обработчиком сессии — какой из них попадает
в сборку, решает Go build tag: `shell_windows_modern.go` (ConPTY)
исключается из legacy-сборки тегом `legacy`, вместо него подключается
`shell_windows_legacy.go` (winpty). Рецепт версий зависимостей для
legacy-сборки — в `BUILD-LEGACY.md`, он отличается от основного go.mod.

Что реально проверил, а что нет — по-честному:
- Сборка на Go 1.20 (сам факт, что весь стек зависимостей на ней
  вообще собирается) — да, причём и под linux (живой тест: пароль,
  шелл-заглушка, SFTP — всё сработало), и кросс-компиляция под Windows.
- Сам winpty.dll/winpty-agent.exe — официальные бинарники, хэши
  сверены, но это чужой прекомпилированный код, не мой — тут я могу
  ручаться за происхождение файла, а не за каждую его строчку, как за
  свой код.
- Живой тест интерактивной сессии именно через winpty — пробовал под
  Wine (с виртуальным дисплеем, иначе даже окно не создаётся), дошёл
  до реального запуска и получил ошибку от самого winpty при попытке
  поднять agent. Почти наверняка это ограничение эмуляции консоли в
  Wine, а не баг в коде — winpty используется в проде десяток лет
  (Git for Windows, старый VS Code, Hyper) именно на настоящих старых
  Windows, и построен на механизме, которого в Wine просто нет в
  таком виде. Но настоящего Server 2008R2/Win7 под рукой у меня нет,
  так что финальную проверку "реально работает" я сделать не могу и
  не буду делать вид, что смог — если при первом запуске на настоящей
  машине что-то пойдёт не так именно с шеллом (а не с подключением
  или SFTP) — присылай, что видишь, разберёмся.

## Важные оговорки

- **Минимальная версия Windows для `winssh-tunnel.exe`: 10, сборка
  1809 (октябрь 2018), или Server 2019.** Для `winssh-tunnel-legacy.exe`
  — Windows 7 / Server 2008R2 и новее (см. раздел выше).
- **tiny-frpc сам себя называет preview-версией** — README проекта
  прямым текстом говорит "not for production, compatibility not
  guaranteed". Последний релиз v0.1.3 — июнь 2024. Протокол SSH Tunnel
  Gateway стабилен с v0.53.0, но живой тест против твоего конкретного
  frps 0.55.1 я сделать не могу — сделай сам, это быстро.
- Пароль по SSH — это принципиально более слабая защита от брутфорса,
  чем ключ, даже с троттлингом. Для личного тестового доступа это
  нормальный компромисс; если когда-нибудь захочешь вернуть ключи —
  это откат одной функции (PasswordAuth → PublicKeyAuth), код в
  предыдущей версии уже рабочий.
- **Шелл и SFTP теперь реализованы**, и вот что реально проверено, а
  что нет — говорю честно, а не "наверное заработает":
  - SFTP — проверил живьём настоящим sftp-клиентом (список файлов,
    скачивание, содержимое совпало), работает по обычному Go
    файловому API (`os.*`), так что на Windows должен вести себя
    так же предсказуемо, как и в тесте.
  - Механику самого шелла (пробрасывание ввода/вывода в обе стороны,
    изменение размера окна, код завершения) проверил живьём — но на
    Linux-заглушке (обычный `/bin/sh`), не на настоящем ConPTY,
    которого просто нет за пределами Windows. Сам ConPTY-код собрался
    под Windows без ошибок и не падает при старте под Wine, но
    настоящий интерактивный сеанс через ConPTY можно до конца
    проверить только на реальной Windows-машине — этого я сделать не
    могу и не буду делать вид, что смог.
  - По умолчанию шелл — `cmd.exe` (как и у штатного Windows
    OpenSSH Server). Если нужен PowerShell — это одна строка в
    `shell_windows.go` (`conpty.Start("cmd.exe", ...)` →
    `conpty.Start("powershell.exe", ...)`), скажи, если поменять.
- Порт sshd теперь целиком берётся из `localPort` прокси "winssh" в
  frpc.toml при каждом запуске — поменял там, перезапустил, без
  пересборки. Если порт занят другим процессом — программа не падает
  целиком (остальные прокси, если есть, продолжат работать), но громко
  пишет об этом в лог; без доступа к логу это легко не заметить.
- host_key, frpc.toml (там теперь и пароль, и токен) — держи рядом
  с бинарником, в .gitignore, не выкладывай публично.
